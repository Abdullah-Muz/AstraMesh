## 2. Analysis columns

**problem.** The paper asks how a decentralized rescheduling framework can keep high-priority task throughput and fair workload when one heterogeneous agent is lost for good. The agents have finite memory, spatially constrained processing windows and only intermittent "relief" (offload) (Problem Statement, p1). The paper studies this through a "Waiter-to-Restaurant" analogy, which it maps onto an Earth-observing LEO constellation. Waiters stand for satellites, tasks for observation requests, sections for orbital regions, memory for the onboard buffer, managers for ground stations, and firing for catastrophic satellite loss (Conceptual Mapping, pp. 2-3). The paper never instantiates the satellite domain. Moving the analogy to satellites is listed as future work (Future Work, p7).

**agent_info.** There are 5 waiters ("agents"). Each has a capability vector (speed, efficiency, accuracy, multitasking), collapsed into C = speed + efficiency + 0.5·accuracy + 0.5·multitasking (Eq. 1, p3). The max is said to be 20, but the attribute ranges are not given. Each agent has a fixed memory M = 500 units, a priority-sorted task queue, a position on a 7-section ring, and a 15-min visit / 90-min cooldown state for Section 6 (pp. 3-4). The paper does not describe what each agent knows about the others. The redistribution step reads every active waiter's memory use, distance, capability and queue length directly, which implies global, perfect, instantaneous information (Task Redistribution Upon Firing, p5). There are no beliefs, no estimates and no health state.

**networking_assumptions.** The paper has **no inter-agent communication model**. It models no messages, crosslinks, bandwidth, latency, packet loss, partitions or topology between agents. The only "communication" is the manager mechanism, which abstracts ground-station downlink (Managers as Ground Stations, p3; Manager System, p4). Three managers sit in sections 2, 4 and 6. When a waiter enters a manager's section, it gets relief with p_help = 0.02, which frees 2-10% of its used memory. The waiter must have completed at least one task, and at most 2 managers can help per waiter per minute. The abstract and introduction say "intermittent connectivity", but in the model that means only this probabilistic downlink relief. It does not mean intermittent coordination links. Redistribution after a firing is "immediate" and uses global state (p5). Delayed or lossy coordination and partitions are therefore not represented.

**physics.** There is no orbital mechanics, power, attitude or space environment, even though the introduction mentions energy reserves and reaction-wheel momentum (p1). Spatial structure is a 7-section circular ring with clockwise motion 1→7→1 (the movement speed is not stated). The distance to Section 6 is d = 6 − s for s ≤ 6, otherwise (7 − s) + 6 (Eq. 3, p4). All 100 tasks originate in Section 6, the analogue of a CONUS-like area of interest. Section 6 access is limited to 15-min visits followed by a 90-min cooldown (p4). Time is 1440 one-minute steps (p3). Task memory cost is uniform by complexity tier: simple U(5,9), standard U(10,19), complex U(20,34), critical U(35,50) (Eq. 2, p3). Progress per minute is Δp_main = U(5,15)·C/20 % and Δp_quick = U(10,25)·C/20 % (Eq. 4-5, p4).

**fault_model.** A single random waiter is "fired". Firing is possible only after a stabilization period, at 5% probability per minute, with at most one firing per run, and it is permanent with no rehire (Dynamic Rescheduling Framework and Firing Event, p4). The text contradicts itself on the start time: firing is "permitted only after 25% (300 minutes)", but the "Timing protection" bullet says no firing "before minute 360" (p4). (Also, 25% of 1440 is 360, not 300.) The figures do not settle this: the firing log lines (Fig. 5-6) print no minute, and the last timestamp before them is minute 206 (Fig. 4). The model does **not** distinguish communication loss from failure, and it has no detection step. The simulator itself pools the fired waiter's tasks at once. Ground truth equals belief, and there are no false positives or detection latency. The fired agent's in-progress task can be re-pooled with no risk of duplication, since it is truly gone. "Firing" stands for "sudden failure or unavailability" (Simulation Overview, p6), but no recovery, degraded or suspected states exist. An earlier version of the authors' model had rehiring (p4). This paper deliberately removes it.

**safety_model.** There is no explicit safety or protection model. The closest analogue is the memory feasibility constraint: a task is accepted only if M_used + cost ≤ 500 (p3). The redistribution ranking puts memory pressure first to "avoid overload", described as buffer saturation (pp. 3, 5). The model has no environmental hazard, safe mode or protection-mode coordination.

**method.** The method can be reimplemented as a comparator from the following:
- **Initial allocation.** 100 tasks are split 40% high / 30% medium / 30% low priority. They are assigned by "priority-aware round-robin" (the procedure is not described in text) (p4). Fig. 1 shows the outcome: task IDs 1-40 are high, 41-70 medium, 71-100 low, and task k goes to waiter (k−1) mod 5, so each waiter gets 8 high, 6 medium and 6 low tasks (20 queued each, Fig. 2).
- **Execution.** In Section 6, a waiter works its highest-priority task as primary. In parallel, if the waiter "is capable of handling multiple tasks" (the threshold is not specified), it works a "quick" task. The quick task is the lowest-memory-cost task among the medium/low tasks in its queue (Eq. 6, p4).
- **Redistribution on firing** (p5):
  1. Pool all of the fired agent's tasks (queued, in-progress, unassigned pending).
  2. Sort the pool by priority, high→medium→low. The tie-break order within a class is not stated.
  3. For each task, mark ineligible any waiter for which M_used + cost > M_capacity.
  4. Rank the eligible waiters lexicographically by the tuple (memory pressure M_used/M_capacity ascending, distance to Section 6 ascending, capability C, presumably descending since "higher ... indicate greater suitability", queue length ascending).
  5. Re-check memory for the top-ranked waiter, assign the task, re-sort that waiter's queue by priority, and recompute M_used as the sum of its task costs.
  6. If no waiter is feasible, the task stays pending until manager relief or task completions free memory.

  Remaining capacity after a firing is written as C_avail = 4×500 − Σ M_cost(t) over reassigned tasks (Eq. 7, p4). The paper says this runs in O(n log n) in the number of tasks (p5). My inference: memory pressure is a continuous ratio, so exact ties are rare and the lower criteria will seldom matter in practice. The paper does not discuss this. Execution is called "decentralized", and the evaluation is framed as CTDE (p5). However, the paper describes no training, and redistribution is a single global pooled assignment. It works in practice as a centralized greedy allocator with global state.

**baselines.** There is **no quantitative baseline comparison**. The only comparison is qualitative. In "prior simulations" (the authors' earlier single-task model, Reliford et al. 2026, AIAA SciTech), "medium-priority and low-priority tasks would remain pending or in progress while all high-priority tasks are completed" (p7). No numbers are given for the prior model. The paper evaluates no CBBA, auction, random, nearest or RL comparator. Comparison against RL and auction policies is future work (p7).

**metrics.** The metrics are task completion counts and rates by priority, and overall completion (Fig. 9, p7; a printed text summary, not a chart). Memory utilization per waiter before and after redistribution (Fig. 2, 7), memory-blocking events (Fig. 5), the event logs (Fig. 3-4) and a per-task status list truncated at task 22 (Fig. 8) are shown only as console screenshots from the same run. The text says the analysis covers "degradation behavior, backlog formation, and fairness" (p2), but it reports no fairness metric (for example Jain's index or the variance of workload). It also reports no backlog statistic and no latency or time-to-reassignment.

**scale.** There are 5 agents (4 remain after a firing), 7 sections, 3 managers and 100 tasks over 1440 one-minute steps (p3). The abstract claims "large-scale simulation" (p1), but the results reported come from **one simulation run**: "In one simulation run, Waiter 4 is fired" (p6). That run completed 66/100 tasks: high 34/40 (85%), medium 14/30, low 18/30 (p7). The paper gives no seeds, Monte Carlo statistics, variance or sensitivity analysis. The visual check confirms that the figures add nothing beyond this single run: no multiple runs, baselines, error bars or fairness/workload measures.

**key_limitations.**
1. The satellite link is only an analogy. There is no orbital, communication or power model, and the transfer to satellites is future work (p7).
2. There is no inter-agent communication, delay, loss or partition model. Redistribution uses instant global knowledge.
3. Failure is a single, oracle-detected, permanent event, with no ambiguity between failure and outage.
4. The evaluation is a single run with no baselines, no statistics and no ablation that isolates the ranking tuple. The claims that dual-task processing improves throughput "substantially" and that the framework "preserves... fair workload distribution" (abstract) are therefore not demonstrated quantitatively. Fairness is never measured.
5. There are internal inconsistencies. Firing start is 300 vs. 360 min (p4). In-text figure references disagree with the captions: a memory-saturation example is cited as "Figure 3" but is Fig. 5; the post-redistribution allocation is cited as "Figure 4" but is Fig. 6-7; the summary is cited as "Figures 5/6" but is Fig. 8-9 (pp. 6-7; confirmed visually). The p3 ranking list orders the criteria distance, capability, memory pressure, queue length, while p5 puts memory pressure first. The CTDE framing has no training component. The figures also show internal anomalies (duplicate and already-completed task IDs in the post-firing queues, mismatched memory values; see "Visual check").
6. Several parameters are underspecified: the attribute ranges, the movement speed, the multitasking eligibility threshold and the round-robin details.
7. Tasks have no deadlines or time windows beyond Section-6 access, and no science value model. Deadlines are future work (p7).

**AstraMesh_overlap.** What P09 shows: a simple, interpretable, rule-based post-loss redistribution heuristic. It pools orphaned tasks, assigns them high-priority-first, and ranks only feasible agents lexicographically by (buffer fill, proximity, capability, queue length). In one 5→4-agent run this heuristic kept 85% of high-priority tasks completed (p7). This is close to AstraMesh's planned "fault-aware rule-based task redistribution" baseline. P09's ranking tuple is a concrete, citable, reimplementable comparator variant, after mapping memory to the AstraMesh storage/energy budget and distance to the next access opportunity.

P09 does **not** establish superiority over any baseline, statistical robustness, or behavior under realistic communication. Its claim to be a "strong competitor for post-fault mission value" is weaker in substance than its framing suggests. It provides one demonstration run and no science-value metric. Against AstraMesh's candidate contributions:
- **G1 (health-belief-aware reassignment, confirmed loss vs. comm outage):** fully open. P09 has an oracle-detected, permanent failure, with no belief states, no suspicion or confirmation, no recovery, and no handling of duplicate execution when a "lost" agent returns.
- **G2 (plan reconciliation across partitions):** fully open. P09 has no crosslinks, no partitions and no message delay or loss, and its redistribution uses one consistent global state.
- **G3 (protection-mode coordination under space weather):** open. P09 has no environment or hazard model and no safe mode.
- **G4 (calibrated predictive estimates in scheduling):** open. P09 uses no predictions or uncertainty. Initial memory is "forecasted" only in the sense that costs are precommitted (pp. 4-5).

Caution: these authors explicitly plan a satellite-domain version compared against RL and auction policies (p7; see also Reliford et al. 2026, AIAA SciTech). Follow-up work may therefore narrow parts of this gap, and AstraMesh should cite P09 as the closest rule-based post-loss redistribution precedent.

## 3. replication_priority
**Medium.** The paper has no comm model or quantitative baselines, so replicating its results adds little evidence. Its redistribution rule, though, is specified precisely enough (p5) to implement cheaply as an extra rule-based comparator, or as a variant of AstraMesh's fault-aware redistribution baseline, and doing so lets reviewers see it was addressed.

## Visual check (2026-11-03)

**What was checked.** All 8 pages were rendered from `data/literature/P09_Reid_2026.pdf` with poppler, and Figures 1-8 were also cropped at 300 dpi. Equations (1)-(7) match the text transcription above. All nine figures are console-output screenshots. None is a bar chart, plot or table.

**What each figure shows (all from the single run in which Waiter 4 is fired):**
- **Fig. 1 (p5), initial allocation.** Per-waiter task lists. Task k goes to waiter (k−1) mod 5. IDs 1-40 are high, 41-70 medium and 71-100 low, so every waiter gets 8 high, 6 medium and 6 low tasks.
- **Fig. 2 (p5), initial memory.** Used/500: W0 419, W1 410, W2 364, W3 477, W4 420. Queued = 20 each. W4 (the agent later fired) holds 420 units. The other four have only 81+90+136+23 = 330 free units, so by the paper's own >250-unit remark (p5) a post-firing backlog was predictable. This is my arithmetic from the figure.
- **Fig. 3 (p6), execution log, minutes 30-99.** [QUICK] completions of medium/low tasks and [COMPLETE] completions of high tasks 2, 3, 4 and 5. Waiter 4 is still active (minutes 49, 77, 98).
- **Fig. 4 (p6), manager log.** Seven relief events freeing 11-27 units (3.4-8.0%, within the stated 2-10%), plus task completions at minutes 198 and 206. The manager lines carry no timestamps.
- **Fig. 5 (p6), firing and blocks.** "[EVENT] Fired Waiter 4." with no minute, followed by 12 [MEMORY BLOCK] lines for high tasks 20, 21, 23, 24 and 25 against waiters at 480-493/500.
- **Fig. 6 (p6), post-firing queues.** WORKING/QUEUED lists for W0-W3. W4 shows WORKING: None and an empty queue.
- **Fig. 7 (p6), post-firing memory.** W0 499, W1 500, W2 496, W3 500, W4 0 (/500). Queued 21, 23, 21, 19, 0. These counts equal the Fig. 6 list lengths, duplicates included.
- **Fig. 8 (p6), final per-task status.** Only tasks 1-22 are visible, all high, all "done", each with a "Current Waiter". The list is cut off.
- **Fig. 9 (p7), summary.** Printed text: High 34/40, Medium 14/30, Low 18/30, Total 66/100. This matches the p7 text.

**Beyond the single run?** No. The figures show no other runs, seeds, baselines, the prior model, error bars, per-waiter completion totals, or any fairness or workload-balance measure.

**New anomalies seen only in the figures (described, not explained by the paper).**
- Fig. 6 queues contain duplicate IDs within one waiter (W0: 11, 16, 21 twice; W1: 15, 17, 22 twice). The same task also appears under several waiters (for example 23 in W1 and W2; 28 in W2 and W3; 31, 33 in W0 and W2; 36 in W0 and W3). Some WORKING tasks also appear in queues (W1 works on and queues 12; W0 works on 6, which W2 also queues).

**What remains uncertain.**
- The actual firing minute, and so which of the two stated rules (300 vs. 360) the code applies.
- Whether the Fig. 6 duplicates and re-queued completed tasks reflect a display artifact or real double-assignment in the simulator. If real, this could affect the 66/100 count. The paper does not say.
- Whether all figures come from the same execution. The text implies one run, but the anomalies above make this hard to confirm.
- Per-waiter completion totals and the medium/low outcomes per task, because Fig. 8 is truncated at task 22.
- Values the paper never prints and the figures do not show: the capability scores C, the attribute ranges and the movement speed.
