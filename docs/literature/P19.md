## 2. Analysis columns

| Column | Content (from the full text) |
|---|---|
| **problem** | Multi-satellite Constellation Observation Scheduling Problem (COSP): a 6-tuple ⟨H, A, R, X, D, C⟩. Agents choose Boolean variables (whether to schedule each "request fulfillment" task) to **maximize the number of satisfied point-target requests**. Each request is a target plus a time window and is satisfied by a single observation. Per-agent constraints are no task overlap and a memory/downlink constraint: data taken before a downlink must not exceed min(onboard memory, downlink capacity) (§3.1, Def. 3.1). COSP is formulated as a multi-variable-per-agent DCOP, using the MVA framework (§3.2). |
| **agent_info** | Key assumption (Table 2, §3.3): agents **know that all other agents exist, and know the full request set and the constellation configuration (orbital planes, fixed biases)**. They do **not** know other agents' variables or capabilities; the text says "Known Constraints: Self Only". Each agent computes its own visibilities and tasks greedily (§5, start). The GND decomposition is computed independently by each agent from shared knowledge, with no communication (§4.2, §4.2.4). |
| **networking_assumptions** | Within a GND sub-problem, each NSS iteration has every agent send the subset of sub-problem requests it satisfied to every other agent in its neighborhood (procedure `message`, §5.3; Prop. 2: O(\|A_N\|) messages of size O(\|R_N\|)). There is **no explicit crosslink topology, visibility, latency, bandwidth or loss model** in the simulation. Message volume is reported as a cost metric only (Fig. 13 counts total bytes; how a byte count maps to link time is not discussed). The text treats limited, unreliable crosslinks as motivation (§1). It lists "Modeling interference and imperfect communication" as future work (§7). The iteration structure appears synchronous (Alg. 5), but the paper does not state this explicitly. The centralized baseline's communication is counted as sending the final schedules, O(L·\|A\|) (§5.4). |
| **physics** | **Supply estimation** for GND uses "simplified geometry such as a spherical Earth and a Keplerian orbit", with bisection over cross-track/right-ascension bounds (§4.2.1, Fig. 3). The paper does not say which propagator or fidelity it uses to compute the actual visibilities and tasks. Sensor slew limits are 60° off-nadir (Planet-like) and 45° (Walker). Each task lasts a fixed 63 s (3 s observation plus 30 s each side for slew/processing). Observation memory is drawn from N(50 MB, 10 MB). Onboard memory is 125 GB. Two ground stations (ASF, Guam) provide constant 62.5 MB/s downlinks (§6.1). Simplifications are stated in §3.1: all downlinks are mandatory, ground stations can serve unlimited simultaneous downlinks, there is no temporal flexibility, and there is no power or attitude model. |
| **fault_model** | Not stated in the text as an experimental element. Single-point failure of a central controller, and satellites leaving or joining, appear only as motivation (§1). Dynamic DCOPs, where agents and requests change, are listed as future work (§7). No failures, dropouts or message loss are simulated. |
| **safety_model** | Not stated in the text. Hard constraints are limited to memory/downlink capacity and non-overlap (§3.1). There is no spacecraft safety, keep-out, power or thermal model. |
| **method** | **GND + NSS.** (a) The **Geometric Neighborhood Decomposition (GND)** heuristic has three layers. The *global supply* layer estimates, per orbital plane, the number of satellites able to see a request: Supply(r,K) = I_{r,K}·\|K\|/o_k (§4.2.1). The *inter-neighborhood* layer (Alg. 1) processes requests in increasing order of supply and assigns each one to the top-n orbital planes by supply ÷ (number of temporally overlapping requests already in that plane's partition), breaking ties by minimum distance to the target. The *intra-neighborhood* layer splits each plane into ρ sub-groups by agent bias b = i mod ρ. It assigns requests by a latitude/longitude grid bias ζ = LatitudeBias + LongitudeBias (§4.2.3, Fig. 4). GND(n) controls overlap (n=1 gives a complete partition) (§4.2.4). (b) **Neighborhood Stochastic Search (NSS)** (Alg. 5, §5.3) is DSA/MGM-like local search that extends the BD algorithm of Parjan & Chien (2023). It starts from a random initial schedule (Alg. 3). Each iteration, it exchanges satisfied-request sets within the neighborhood. It then stochastically updates assignments, with m = the number of agents that satisfied r per the broadcast: if unassigned, it assigns when m = 0 and stays unassigned when m > 0; if assigned, it unassigns with probability P_u = 0.7 when m = 0, or with probability (m−1)/m when m > 0. Insertion may evict the conflicting task with the closest start time. Iterations are capped at 20, with a 0.001% convergence threshold (§6). |
| **baselines** | **Fully decentralized, no communication:** Random, Greedy Start Time, and Greedy Portfolio, which samples one of four heuristics: random, start time, memory, off-nadir (§5.1.2). **Decentralized with communication:** BD (Parjan & Chien 2023) and NSS-Random (random decomposition) (§5.3). **Centralized:** Squeaky Wheel Optimization (SWO) with random fulfillment selection (Alg. 4, §5.2). **Optimal reference:** centralized branch and bound, on small instances only (§6.2.2). There is no auction, CBBA or MILP baseline. |
| **metrics** | Small instances: optimality gap in % satisfied requests, run time (ms) and message volume (KB) (Tables 4-5). Large instances: % satisfied requests (Fig. 11), make-span execution time, reported as the max over agents for decentralized methods (Fig. 12), and total message volume in bytes (Fig. 13). Figs. 11-13 are per-instance scatter plots with a fitted line per algorithm; no error bars or significance tests. Figs. 12-13 use a log y-axis with an extra "0" tick, where the no-communication baselines sit at about 1 ms and 0 bytes (read from plot). GND diagnostics: request-supply distribution (Fig. 9) and normalized supply-estimation error (Fig. 10). |
| **scale** | Two simulated LEO constellations (§6.1.1). "Planet" has 200 satellites in 4 planes at 600 km: 2×95 at 95° inclination and 2×5 at 52°. "Walker" has 6×14 at 88° plus an overlay of 2×12 at 51.6°; the paper elsewhere says 108 agents (§6.2.1). There are 634 ground targets (cities and volcanoes), a 24 h horizon and 2 ground stations. Large instances: about 1,800-5,800 requests for Planet and about 1,900-7,000 for Walker (read from Fig. 11; Walker instances fall on about nine discrete request counts), giving "millions of variables" (§1), over 100 random instances. Small instances: 400-500 requests over 50 instances (§6.2.2). Java simulation (§6.2.3). Hardware is not stated. |
| **key_limitations** | (i) Communication is costed but not modeled: no link availability, delay or loss (§7 future work). (ii) Static, one-shot scheduling over a fixed horizon, with no dynamic or online re-planning (§7). (iii) Simplified downlink model and fixed-duration tasks without temporal flexibility (§3.1, §5.3). (iv) GND relies on orbital-plane structure. The authors admit neighborhood selection "exploits specifics of our domain" (§4.2.2), and give no bound guaranteeing reduced sub-problem size (§4.2.2). (v) No quality guarantees (§7). On large instances, decentralized methods leave a gap to centralized SWO, and the text says the best NSS is about 3% below BD in satisfaction (§6.2.3). Read from the Fig. 11 fit lines, that holds for Planet (about 2.5-3.5 points) but understates Walker, where the gap grows from about 4 points at ~1,900 requests to about 7-8 points at ~7,000. (vi) The claim that supply-estimation error has "no degradation" on performance when exact supply is used is stated but not shown in a table or figure (§6.2.1). Fig. 10 shows only the size of the estimation error, not the exact-supply vs. estimated-supply scheduling comparison. (vi-b) The text's efficiency ratios ("nearly 2 orders" faster than BD; message volume "around 2 orders" below BD) fit Planet at the larger sizes but not Walker, where the plotted gaps are about 1 order or less (Figs. 12-13, read from plot). (vii) On small Walker instances, simple Random (0.188% gap) beats every NSS variant; the best is NSS-GND(4) at 0.236% (Table 5). The authors attribute this to under-constrained small instances. (viii) No code or data availability statement was found. |
| **AstraMesh_overlap** | Partial and cautious. The overlap is in *problem class*: decentralized, constraint-aware scheduling of observation requests across satellites, with message volume treated as a first-class cost, and with static greedy, centralized and communication-based decentralized baselines alongside an optimality reference. The *regime is very different*. P19 targets 108-200 satellites, thousands of point-target requests and plane-based decomposition, and it does not model crosslink windows or loss. AstraMesh has 4 CubeSats, constrained crosslinks, ionospheric observations, and auction/CBBA baselines that P19 does not include. GND's decomposition offers little at N=4. NSS-style stochastic local search without decomposition (essentially BD, with resource-aware eviction) could be a candidate additional decentralized comparator. P19's practice of reporting message volume and make-span next to solution quality is directly reusable for AstraMesh's evaluation design. |

## 3. Relationship to P02 (ICAPS 2024)

The JAIR paper states its relationship to the conference version explicitly (§1, p. 172): *"This article extends on a previously published conference paper (Zilberstein et al., 2024b). We provide a more in-depth discussion, extended theoretical analysis, broader experimental results and analysis, and improvements and variations of the initial algorithms and heuristics published."* Its reference list gives P02 as ICAPS Vol. 34, pp. 716-724.

I skimmed P02 from the authors' JPL-hosted copy (https://ai.jpl.nasa.gov/public/documents/papers/Zilberstein-ICAPS-2024.pdf, 8 pages + references). It has the same title and the same four authors. The publisher page, ojs.aaai.org, blocked automated access with a bot wall, so I did not verify that the JPL copy is identical to the proceedings version. Concrete differences I observed:

- **GND algorithm.** P19 itself says that in the earlier work "the heuristic H was directly the supply, Supply(r,K), and only n = 1 was considered" (§4.2.2). In P02, a request goes to the plane with the most agents having non-zero supply. P19 adds temporal-overlap-aware delegation (supply ÷ overlapping requests, Alg. 1) and the GND(n) incomplete/overlapping partitions. P02's intra-neighborhood layer also used a "sub-supply" bias heuristic alongside the target-position bias. P19 uses only the latitude/longitude bias with explicit Z_i weights.
- **Experiments.** P02 evaluates only the 200-satellite Planet-like constellation and fixes ρ = 5 by grid search. P19 adds the **Walker** constellation (108 satellites), GND(1/2/4/8) variants, a supply-distribution figure (Fig. 9) and a supply-estimation-error figure (Fig. 10). In P02, BD is run on small instances only, "due to communication constraints". P19 also reports BD on large instances (Figs. 11-13), along with large-instance message-volume plots.
- **Baselines.** P02 included a fully decentralized "Decomposition Heuristic" baseline (GND followed by Greedy Start Time). I did not find it in P19.
- **Presentation and metrics.** P19 adds a formal related-work complexity table (Table 1), the t-COSP toy problem with Proposition 1 (§4.1), formal Propositions 2-3, an off-nadir task-construction description and pseudo-code for Algorithms 1-5.
- **Reporting.** P02 reports time as the average per agent and messages as counts (P02 Table 2). P19 reports max-over-agents time and messages in KB/bytes. The numbers are **not directly comparable** across the two papers. For example, on small Planet instances P02 gives NSS-Decomp a 0.409% gap, while P19 gives NSS-GND(1) 3.072% and NSS-GND(2) 1.713% (P19 Table 4). The P19 instance generator and protocol also changed: the campaign is a random ≥75% subset of targets. P19 does not explain this discrepancy.
- **Headline claim.** P02 says NSS is "comparable in performance to the centralized approach, averaging just a 3% satisfaction decrease". P19 instead reports "there remains a gap between any of the decentralized approaches" and the centralized one, plus a 3% gap between the best NSS and BD (§6.2.3).

**Citation recommendation:** cite P19 as the primary, archival reference and treat P02 as its superseded precursor.

## 4. replication_priority

**Medium.** The NSS update rule and the baselines are specified precisely enough to reimplement. Partial replication would be useful as an extra decentralized local-search comparator alongside auction/CBBA, and as a template for message-volume reporting. However, GND's plane-based decomposition, the 200-satellite scale and the absence of a crosslink model make full replication of little relevance to a 4-CubeSat, crosslink-constrained mission.

## Claims vs. demonstrated results

- **Demonstrated** (Tables 4-5, Figs. 11-13): on small instances, NSS-GND is within about 0.2-3% of optimal. It sends roughly 6-110× fewer KB than BD (Planet: 107-208 vs. 11,895 KB; Walker: 122-412 vs. 2,451 KB). NSS-GND(2/4/8) beat BD on gap in both tables, while NSS-GND(1) does not. On large instances, NSS-GND beats the no-communication baselines and NSS-Random on satisfaction, but in Planet only by about 1-4 points over Random (read from Fig. 11). Read from Figs. 12-13, efficiency versus BD is constellation-dependent:
  - **Planet:** about 1-2 orders of magnitude faster (BD ~20-260 ms vs. NSS-GND ~1-5 ms) and about 1.5 orders fewer bytes (BD ~2-3×10^7 vs. NSS-GND ~0.3-1×10^6).
  - **Walker:** only about 0.7-1 order faster (BD ~10-110 ms vs. NSS-GND ~3-21 ms) and about 0.5-1 order fewer bytes (BD ~0.6-1.1×10^7 vs. NSS-GND ~0.4-1.8×10^6).

  Satisfaction is about 3 (Planet) to 4-8 (Walker) points below BD, and below SWO.
- **Claimed but not demonstrated in this paper:** suitability for onboard or flight deployment, robustness to single-point failure, generality to other domains (multi-rover, MAPF, UAVs), and the statement that "this error has no degradation on the scheduling performance" when exact supply is used, for which no data are shown.

**What changed in this review.**
- **Coverage note.** The earlier note said figures were not inspected. It now records the visual check.
- **Large-instance request range.** This was "about 2,000-7,000". It is now about 1,800-5,800 for Planet and about 1,900-7,000 for Walker.
- **"3% gap to BD".** This was accepted as given. Fig. 11 supports it for Planet only. For Walker the gap is about 4-8 points (key_limitations v; Claims section).
- **Efficiency vs. BD.** "About 2 orders of magnitude faster, with about 2 orders lower message volume" was stated as demonstrated. The plots support about 1-2 orders for Planet only. Walker shows about 1 order or less, and at the smallest Walker sizes the BD and NSS-GND(4)/(8) time fits nearly meet (about 10 ms).
- **NSS-GND vs. NSS-Random messages.** The text calls NSS-GND "slightly less than NSS-Random". That is true for Walker, but in Planet NSS-GND is about 5-6× lower.
- **"An order of magnitude slower" claim (§6.2.3).** The text says NSS is an order of magnitude slower than the fully decentralized baselines. That does not hold for NSS-GND(1) in Planet (about 0.7-3 ms vs. about 1 ms).
- **Supply-estimation error.** Earlier wording implied nothing was shown. Fig. 10 does show the size of the error, but the exact-supply performance comparison is still not shown.
- **Small-instance message advantage.** "About an order of magnitude" is replaced by the table ratios (about 6-110×).
- **NSS stochastic-update rule.** The wording now matches the four cases in the paper (p. 193).

**What remains uncertain.**
- **Plot-read precision.** Values are read by eye from rendered plots; on the log axes, values are only reliable to within a factor of about 2.
- **Overlapping series.** In Planet, NSS-GND(4) and NSS-GND(8) overlap, and Random and Portfolio Greedy use similar light colours, so their individual fit lines are hard to separate.
- **Table 4 typo.** Table 4 prints NSS-Random's message volume as "1, 4303.712" KB, which is probably 14,303.712 KB. This is not confirmed.
- **Table 4/5 header typo.** "Portfolio Gredy" is a typo in both tables and does not affect the values.
- **Incomplete sentence on p. 183.** The supply section contains an incomplete sentence ("In these instances, an offset We compute ..."), so how unevenly spaced planes are handled is not fully stated.
- **Statistics.** No error bars, confidence intervals or significance tests are given for Figs. 11-13, so the reliability of small gaps (e.g. NSS-GND vs. Random in Planet) cannot be judged from the paper.
